# B站评论人工审核工具：产品功能审查

审查日期：2026-08-22

## 产品主线

唯一默认工作流：

1. 选择账号。
2. 从创作中心评论时间线读取最近 10 到 50000 条评论，默认 500。
3. 登录后自动识别账号 UID 和昵称；排除已发送、已有草稿、UP 已回复、账号自己的评论和明确过滤项。
4. 将评论及必要上下文交给豆包，保留豆包原始候选。
5. 用户逐条勾选批准。
6. 再次确认后，只把本次勾选项串行发送到 B站。

任何后台监控都只能生成草稿，不能绕过人工批准自动发送。

## 功能取舍

| 现有功能 | 产品决定 | 原因 |
|---|---|---|
| 创作中心最新评论时间线 | 保留，作为默认且唯一可见的抓取入口 | 满足跨视频、按时间从新到旧处理 |
| 本次读取数量 | 保留，默认最多扫描 500 条原始评论，正式产品提供 10 到 50000 的完整档位 | 调试环境可用临时硬限额，不能删减正式能力 |
| 连续无新增停止 | 默认开启，连续 3 个成功页面没有新增最终待生成评论时停止；审核页可关闭 | 防止进入历史区间后继续无效翻页；前面多页是旧记录但后面仍可能有遗漏时允许完整扫描 |
| 时间范围 | 保留，相对时间由后台在每轮任务开始时计算 | 开启提前停止时与数量、连续无新增页和列表末尾先碰到哪个边界就停止；关闭时不受连续空页限制 |
| B站永久不可回复 | 评论区关闭、稿件失效、评论不存在等明确错误标记为 `unavailable` | 后续扫描、生成和发送都跳过；网络超时、429 等暂时错误不能误标 |
| 豆包系统提示词、模型、推理模式 | 保留，移入“豆包设置” | 直接决定候选回复 |
| 豆包批次、并发、请求间隔、重试 | 保留，移入高级设置 | 只影响豆包生成；不影响 B站串行限制 |
| 单条重新生成 | 保留 | 用户不满意时显式触发，默认不重复消耗 Token |
| 草稿批准和发送 | 保留并强化门禁 | 未勾选、未确认绝不发送 |
| 评论时间、作者、视频、父评论上下文 | 保留 | 是判断回复是否合适的必要信息 |
| 关键词、长度、用户过滤 | 改名为“送豆包前预筛选”，移入高级设置 | 它们不发送回复，只决定是否进入生成 |
| B站请求间隔、重试 | 保留，移入高级设置 | 抓取和发送必须串行并节流 |
| Cookie 自动刷新 | 保留 | 长期使用所需 |
| 日志和历史 | 保留，按账号隔离 | 排错和防重复发送所需 |
| 密码保护 | 从前端移除 | 当前实现未经产品验证，不作为可见功能交付 |
| `reply.enabled` | 改名为“草稿监控” | 当前含义不是自动回复 |
| `max_process`、审核页“本次读取” | 合并 | 两个入口表达同一件事，避免互相覆盖 |
| `review_since`、审核页“时间范围” | 合并 | 同上 |
| `only_new` | 删除可见配置 | 当前主线已通过草稿、历史和 UP 回复状态去重 |
| `prefix` | 默认流程删除 | 发送时拼接会修改豆包原文，违背“原样发送” |
| 自动点赞评论 | 从默认产品移除 | 与人工审核回复无关，增加外部写操作 |
| 回复后点赞用户视频 | 从默认产品移除 | 高风险且与主任务无关 |
| 指定 `only_bvid` | 移入兼容/诊断模式 | 属于旧逐视频路径，不应干扰时间线主线 |
| 视频页数、评论页数、嵌套回复深度 | 移入兼容/诊断模式 | 仅服务旧逐视频抓取 |
| 视频缓存页面和“清除视频缓存” | 从默认界面移除 | 时间线主线不依赖视频列表 |
| `legacy/` | 不进入发布包 | 集中保存旧自动启动器、旧 Tk 配置器、旧单文件测试、旧限流监控和双实例 BAT，避免与正式产品入口混淆 |

## 多账号边界

- 一个 Windows 应用、一个本地服务、一个内部端口。
- 产品设置保存在共享数据根目录。
- 每个账号有独立目录，至少隔离：
  - `config.toml`
  - `bilibili_cookie.json`
  - `review_drafts.json`
  - `history.json`
  - `video_cache.json`
  - `logs/`
  - 机器人运行状态和审核互斥状态
- 所有账号路由必须携带明确账号 ID，不能仅依赖进程级全局单例。
- 二维码状态和日志事件必须标记账号 ID，防止切换账号后串到当前页面。
- 账号可以分别启停草稿监控；开关按账号持久化，当前账号开启后重启 EXE 会自动恢复。
- 抓取和发送在单个账号内部串行；监控只生成草稿，不自动发送。
- 豆包配置和 API Key 按账号保存，也可由产品进程环境变量统一覆盖；API Key 不写入 EXE。

## 生命周期和互斥

- 同一账号生成中：禁止再次生成、发送、修改会影响当前生成的账号配置。
- 同一账号发送中：禁止生成、再次发送、切换或删除该账号。
- 配置在任务开始时做快照；任务期间保存的新配置在任务结束后生效。
- 退出时停止新任务，等待当前单次 B站请求结束，持久化草稿和历史。
- 上次退出时处于 `sending` 的草稿启动后标为“发送结果待核对”，绝不自动重发。
- 上次退出时处于 `generating` 的草稿恢复为未批准状态，可手动重新生成。
- 清空历史改为原子写入空数组，不直接删除文件。

## 主题和首次启动

- 主题提供“跟随系统、日间、夜间”，默认跟随系统。
- 首次启动先创建账号并扫码登录，再配置豆包，不显示旧的高级配置墙。
- 主界面顶部始终显示当前账号、登录状态、监控状态和当前操作。
- 普通用户不需要知道端口、Python、BAT、数据目录或命令行。

## 发布边界

- Windows x64 单目录发布包，入口 EXE 双击启动。
- 首选可审计、稳定的 onedir 打包；不为了单文件外观牺牲启动稳定性。
- 数据写入 `%LOCALAPPDATA%`，不能写入 Program Files 或打包目录。
- 发布包不包含 Cookie、API Key、历史、草稿、日志或开发测试数据。
- 页面不回显已保存的 Cookie、Refresh Token、API Key 和密码哈希；清除凭据必须显式确认。
- Socket.IO 浏览器客户端随发布包本地提供，离线启动不依赖 CDN。
- 旧版数据只允许复制导入为新账号，不覆盖、不删除来源目录。
- EXE 必须用干净数据目录验证首次启动、重启持久化、双账号隔离和审核门禁。
